# 09. What extraction does to a sentence

Research for ticket 09. Constraint: ADR 0001 (docs/adr/0001-every-flag-cites-its-source.md) says a cited sentence must be found "word for word" in the stored text, and that the matching rule for "the same sentence" has to be written down and tested. This note lists what changes between the source document and the stored text, and offers candidate normalisations with their risks. **No rule is decided here; the owner approves it.**

Sources were read on 2026-10-31 from the `master` branches of pdf.js and mammoth.js. Line numbers drift, so search for the quoted identifier instead.

## 1. pdf.js `getTextContent`

What the API returns ([src/display/api.js](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js)): `items[]`, each with `str`, `dir`, `transform`, `width`, `height`, `fontName` and `hasEOL` ("Indicating if the text content is followed by a line-break"). There are two options. `includeMarkedContent` defaults to false. `disableNormalization` defaults to false: "When true the text is *not* normalized in the worker-thread."

| Effect | What the source shows | Consequence for matching |
|---|---|---|
| **No real line or paragraph structure** | A PDF has no paragraphs, only positioned glyphs. `appendEOL()` sets `hasEOL` when the next glyph jumps too far vertically or horizontally ([src/core/evaluator.js](https://github.com/mozilla/pdf.js/blob/master/src/core/evaluator.js), `compareWithLastPosition`). Redline's own code decides whether `hasEOL` becomes `\n`, a space, or nothing. | A wrapped sentence arrives split across lines. A model quoting it will write one space where the stored text has `\n`, or vice versa. |
| **Spaces are synthesised from geometry** | With the default `keepWhiteSpace = false`, whitespace glyphs are *not* emitted. The comment reads "Don't push a ' ' ... it will be done (if required) in next call to compareWithLastPosition". Gaps are classified by fractions of font size (`TRACKING_SPACE_FACTOR = 0.102`, `SPACE_IN_FLOW_MIN/MAX_FACTOR = 0.102/0.6`, `NOT_A_SPACE_FACTOR = 0.03`), and a `" "` is pushed when the gap qualifies. | Spaces can be **missing** (tight kerning: "thePurchaser"), **extra** (letter-spaced headings: "N O T I C E"), or **doubled**. The original space character is lost, so a NBSP (`\s` matches U+00A0) comes back as an ordinary space or as nothing. |
| **Invisible format marks dropped** | Glyph category comes from `/^(?:(\s+)\|(\p{Mn}+)\|(\p{Cf}+))$/u` ([src/core/unicode.js](https://github.com/mozilla/pdf.js/blob/master/src/core/unicode.js), `getCharUnicodeCategory`). Glyphs with `isInvisibleFormatMark` (category Cf: U+200B zero-width space, U+200D ZWJ, U+2060, and U+00AD soft hyphen, which is also Cf; U+FEFF matches `\s` first, checked in Node, so it is treated as whitespace) are skipped with `continue`. | Zero-width characters normally disappear from PDF text. Separately, `mapSpecialUnicodeValues` maps the font char code 0x00AD to 0x002D (hyphen). That applies to the font code drawn on screen. Whether a soft hyphen reaches `str` as nothing or as `-` is **unconfirmed; test with a fixture**. |
| **Partial NFKC (ligatures etc.)** | When normalisation is enabled, `runBidiTransform` calls `normalizeUnicode(text)` ([src/shared/util.js](https://github.com/mozilla/pdf.js/blob/master/src/shared/util.js)). This applies `.normalize("NFKC")` **only** to a fixed set: U+00A0 NBSP, U+00B5 µ, U+2000–200A spaces, U+202F, U+2126 Ω, the U+FB00–FB06 Latin ligatures (ff, fi, fl, ffi, ffl, st), and Hebrew/Arabic presentation forms. The comment says "most the chars here contain some ligatures". Glyph names like `f_t` and `T_h` are mapped by stripping `_`. | Ligatures fi/fl normally come out as two letters. If a font lacks a ToUnicode entry for a ligature glyph, the text may be missing or wrong (`_simpleFontToUnicode` falls back to "heuristics"). That is a broken text layer, not a matching problem. Curly quotes, dashes, superscripts and ½ are **not** touched by pdf.js extraction. |
| **Reading order = content-stream order** | Items are pushed as operators are read, with no visual sorting (evaluator loop over `preprocessor.read`). | **Multi-column layouts** may interleave columns, or a sentence may continue after the other column's text. Text boxes and form XObjects appear where they are invoked. |
| **Headers, footers, page numbers included** | `beginMarkedContent` tags (including `/Artifact`, which tagged PDFs use for running headers and footers) are only *reported* when `includeMarkedContent` is true. No filtering of artifact text was found in the text path. | A sentence that crosses a page break will contain "Page 4 of 12" or the running header in the stored text. Filtering that out is Redline's job, and it only works for tagged PDFs. |
| **Footnote markers inline** | A superscript marker is just a small glyph. It is extracted as an ordinary digit with no superscript flag (only `transform`/`height` hint at it), and the footnote body sits at page bottom. | "...the Fee¹ is payable" is stored as "the Fee1 is payable" or "the Fee 1 is payable". A model will usually drop the "1". |
| **End-of-line hyphenation** | The extractor keeps the hyphen and sets `hasEOL`. In PDF the soft/hard distinction is usually gone at creation time: a line-end hyphen is a drawn U+002D. pdf.js's **own find bar** dehyphenates for search only ([web/pdf_find_controller.js](https://github.com/mozilla/pdf.js/blob/master/web/pdf_find_controller.js) `normalize`). It removes `-\n` only between letters (`\p{Ll}-\n(?=\p{Ll})\|\p{Lu}-\n(?=\p{L})`; the comment says "likely here to mark a break in a word"), keeps the hyphen but drops the newline otherwise ("could be, for example, in a compound word or in a date"), and replaces every other `\n` with a space ("foo\nbar is likely equivalent to foo bar"). | This is Mozilla's precedent for a search-time rule. Its known failure: a real compound split at the line end ("non-\ncompete", "sub-\ncontractor") is joined to "noncompete". |

pdf.js find also maps curly quotes ‘’‚‛“”„‟ to straight quotes, U+2010 to `-`, and ¼½¾ to "1/4" etc. (`CHARACTERS_TO_NORMALIZE`), and offers case and diacritic insensitivity as user toggles. This is search behaviour in the viewer, not extraction.

## 2. DOCX via mammoth.js

`extractRawText` "will ignore all formatting in the document. Each paragraph is followed by two newlines" ([README](https://github.com/mwilliamson/mammoth.js/blob/master/README.md)). The source ([lib/raw-text.js](https://github.com/mwilliamson/mammoth.js/blob/master/lib/raw-text.js), [lib/docx/body-reader.js](https://github.com/mwilliamson/mammoth.js/blob/master/lib/docx/body-reader.js)) shows the following.

- **Runs are concatenated.** Word splits one sentence into many `<w:r>` runs (formatting, spell-check `w:proofErr`, revision IDs). `w:proofErr`, `w:bookmarkEnd`, comment ranges and `w:lastRenderedPageBreak` are in the ignored list, and `w:smartTag`, `w:sdt` (content controls) and `w:hyperlink` are read through to their children. Run splitting therefore does **not** break sentences in mammoth's output. It does break a naive `document.xml` reader that joins `<w:t>` per run or inserts separators between them.
- **Tracked changes = "accepted" view.** `w:ins` and `w:moveTo` are read as normal content, while `w:del` and `w:moveFrom` are ignored, along with deleted table rows. Stored text is the document *as if all changes were accepted*. That may not be what the user sees if their Word view shows markup or "Original". **Owner question:** is that the intended view?
- **Fields.** `w:fldChar` and `w:instrText` are parsed, and only HYPERLINK and FORMCHECKBOX are interpreted. The field's displayed result runs (between `separate` and `end`) are kept as text, so cross-references, dates and auto-numbers come through as the last-rendered value. **Automatic list numbering (`w:numPr`) is not text at all**, so clause numbers like "4.2(a)" are absent unless typed by hand.
- **Line breaks vanish in raw text.** `w:br` becomes a `Break` element with no children, and `convertElementToRawText` returns `""` for it. A manual line break inside a sentence ("thirty<br>days") is stored as "thirtydays". The same happens to page and column breaks. Tabs become `\t`.
- **Hyphens kept as Unicode.** `w:softHyphen` gives U+00AD and `w:noBreakHyphen` gives U+2011, both left in the text. Word curly quotes, en/em dashes and NBSP are literal characters in `<w:t>` and pass through unchanged.
- **Footnotes, headers, comments.** Footnote and endnote references produce `""` in raw text (no marker digit), and note bodies are not in the body text. Comments are ignored by default. Headers and footers are not read (no header/footer part handling in `docx-reader.js`). Text boxes are emitted "as a separate paragraph that appears after the paragraph containing the text box" (README), which moves the text box's sentences away from their place in the host paragraph. A deleted paragraph mark (`deletedParagraphContents`) merges two paragraphs with no separator, which is another lost boundary like `w:br`.
- `mc:AlternateContent` reads the `mc:Fallback` branch.

## 3. Pasted text

The browser gives the string as copied. It can carry NBSP, U+200B, U+00AD, curly quotes, CRLF and hard line wraps from the source app, unchanged.

## 4. Prior art for verification

- **Unicode TR15** ([unicode.org/reports/tr15](https://www.unicode.org/reports/tr15/)). §1.1 says canonical equivalence is "fundamental" and compatibility equivalence "weaker". §1.2 says "Normalization Forms KC and KD must not be blindly applied to arbitrary text" because they "may remove distinctions that are important to the semantics of the text". Examples: the fi ligature becomes f+i, i⁹ becomes i9, ¼ becomes 1/4. NFC is safe and lossless for meaning. Full NFKC turns superscript footnote markers and exponents into plain digits.
- **Text fragments** ([wicg.github.io/scroll-to-text-fragment](https://wicg.github.io/scroll-to-text-fragment/), a WICG Community Group report, not a WHATWG standard). Matching uses a base-character comparison: "Intuitively, this is a case-insensitive search also ignoring accents, umlauts, and other marks". Matches stop at block boundaries and use UAX#29 word bounds. It is built for *locating* text, so it trades precision for recall. Its case and diacritic folding is too loose to count as proof of a quote.
- **Claude API citations** ([platform.claude.com/docs/en/build-with-claude/citations](https://platform.claude.com/docs/en/build-with-claude/citations)). The API avoids string matching entirely. Documents are "chunked into sentences", the model cites chunk indices, and `cited_text` is extracted by the API, so "citations are guaranteed to contain valid pointers to the provided documents". This is not available through the CLI (ADR 0001). The same *design* works locally, though: pre-segment the stored text into numbered sentences, have the model return a sentence ID plus its quote, and verify the quote against that one sentence. The search space becomes one sentence instead of the whole document.

## 5. Candidate normalisations (applied identically to stored text and model quote)

Each candidate is a proposal, not a decision. "Collision risk" means the chance that two sentences with different legal meaning compare equal.

| # | Normalisation | Fixes | Collision risk |
|---|---|---|---|
| N1 | Unicode **NFC** | Composed vs decomposed accents (é) | None in practice. Canonical equivalents are the same text (TR15 §1.1). |
| N2 | Collapse every run of whitespace (space, `\t`, `\n`, `\r`, NBSP U+00A0, U+2000–200A, U+202F, U+3000) to one space; trim ends | Line wraps, PDF space synthesis, NBSP, paragraph gaps | Very low. Whitespace carries no legal meaning. Does **not** fix *missing* spaces ("thePurchaser") or *extra* ones ("N O T I C E"). |
| N3 | Delete zero-width and format chars: U+200B–200D, U+2060, U+FEFF, U+00AD soft hyphen | Invisible characters from paste/DOCX | Very low. They are invisible by definition. |
| N4 | Fold quotes: ‘ ’ ‚ ‛ ′ to `'`, “ ” „ ‟ ″ to `"` (same set as pdf.js find) | Model writes straight quotes, document has curly | Low. Watch for ′ ″ as feet/inches or minutes ("6′" vs "6'"), which are equivalent in meaning anyway. |
| N5 | Fold dashes: U+2010, U+2011, U+2012, U+2013, U+2014, U+2212 to `-` | Model writes `-` for an en/em dash | Low, but not zero. "10–20" vs "10-20" is the same range. An em dash used as a clause break is still punctuation, so the words are unchanged. |
| N6 | Fold the U+FB00–FB06 ligatures to their letters (NFKC on that block only) | Ligature glyphs if extraction was run without pdf.js normalisation, or in pasted text | None. Matches what pdf.js already does by default. |
| N7 | Dehyphenate `letter-\nletter` **in the stored text before N2** (pdf.js find rule) | Line-end hyphenation in PDFs | **Medium.** Joins genuine compounds split at a line end ("non-\ncompete" becomes "noncompete"). Safer variant: accept a quote if it matches *either* with the hyphen kept or with it removed at that one position. Must only act at an extracted line end, never mid-line. |
| N8 | Strip footnote markers | "Fee¹" vs "Fee" | **High as a general rule.** Indistinguishable from real digits in PDF output ("Section 4 1" vs "Section 41"). Only feasible where the extractor flags the glyph as superscript (pdf.js `height`/`transform`), and that is unproven. |
| N9 | Remove running headers/footers/page numbers | Sentences crossing a page break | Medium. Heuristics (repeated line at the same y on each page, `/Artifact` tags) can delete real text. Better done at extraction, so the stored text and the displayed text agree, than at match time. |
| N10 | Full **NFKC** | Everything N6 does, plus width variants | **Do not use.** TR15 §1.2: superscript ² becomes 2, ½ becomes 1/2, so "10²" matches "102". |
| N11 | Case folding | Model capitalisation drift | **Do not use.** Case matters in contracts: defined terms ("the Company" vs "the company"), "SHALL", party names. |
| N12 | Strip punctuation or digits / match ignoring diacritics (text-fragment style) | Higher recall | **Do not use.** "$1,000.00" vs "$100000", "30" vs "3.0", "not later than" vs "not, later, than", "résumé" vs "resume". Any of these changes meaning. |

**Match granularity (high risk if substrings are allowed).** Before any normalisation, the rule has to say what the quote may cover. A *truncated* quote, "The Client may terminate this Agreement at any time" where the sentence continues "...unless Section 9 applies", passes a substring check while dropping the qualifier that reverses its meaning. An *ellipsis splice* (`...` or U+2026) glues two places together, so it must count as an altered quote and never as a wildcard. Options: the quote must equal one whole segmented sentence (or a run of consecutive whole sentences), or the substring must start and end on sentence boundaries. The sentence-ID design in section 4 fits naturally here.

Not a normalisation, but a check the rule needs. **Mammoth's `w:br` becoming `""`** and **pdf.js's missing spaces** both *remove* a word boundary. No safe normalisation restores it. Options are to fix it at extraction (emit `\n` for `Break` when building raw text, or use `keepWhiteSpace`-style handling), or to compare with all spaces removed as a last resort. Removing all spaces makes "the rein" equal "therein", so it carries a medium collision risk.

## 6. Open questions for the owner (do not guess)

1. Must a quote be a whole sentence, or can it be a substring that starts and ends on sentence boundaries? Which candidates from section 5 make up the approved rule, and is N7 acceptable in its "either form" variant?
2. Should the **displayed** quote be the stored text span (after mapping back) rather than the model's string? This keeps the reader's word-for-word check honest when normalisation was used.
3. For DOCX with tracked changes, should Redline analyse the accepted view (mammoth default), reject the upload, or warn?
4. Is a sentence-ID scheme (section 4, citations design) acceptable as the primary check, with string matching inside that sentence?
5. Should headers, footers and page numbers be stripped at extraction (affects every capability, not only citations)?

## 7. Fixtures this implies (for the ADR 0001 tests)

PDF with a wrapped sentence, a line-end hyphen in a plain word, a line-end hyphen in a compound, an fi ligature, a superscript footnote marker, two columns, a sentence crossing a page footer, and a letter-spaced heading. DOCX with tracked insert/delete, a manual line break mid-sentence, a soft hyphen, a no-break hyphen, curly quotes, an em dash, auto-numbered clauses, and a text box. Pasted text with NBSP and U+200B. Negative cases: model quote with "30" changed to "60", "shall" changed to "may", "not" dropped, defined-term case changed, trailing qualifier ("unless...") dropped, two clauses spliced with an ellipsis. Each of these must fail verification.
